C# 15: Union Types, Closed Hierarchies, and the One Value™ That Isn't Any of Them

2026-11-09 #csharp #dotnet #fsharp #elm #union-types #type-safety #functional-programming #domain modeling

.NET 11 launches this week at .NET Conf, and with it comes C# 15. The headline feature, at least for someone like me, is union types. People have been asking for discriminated unions in C# for years, and now there’s a union keyword in the language.

A disclaimer before we start: C# is not my home turf. I write Elm on the frontend, I’ve done a fair bit of Kotlin, and I hope to write a lot more F#. So this is an outsider looking at a feature I care about, in a language I don’t use daily. If I’ve missed some well-known C# idiom below, I’d genuinely like to hear about it.

What I can do is run the code. Every snippet and every compiler message below comes from SDK 11.0.100-rc.3, the last release candidate before GA. No preview flags needed, actually: C# 15 is the default language version for net11.0, and a single .cs file runs with dotnet run file.cs 🤓.

The basics

1public record Cat(string Name);
2public record Dog(string Name, int Age);
3
4public union Pet(Cat, Dog);

That’s it. A Pet is either a Cat or a Dog, and you get an implicit conversion from each:

1static string Describe(Pet pet) => pet switch
2{
3    Cat c => $"{c.Name} the cat",
4    Dog d => $"{d.Name} the dog, age {d.Age}",
5};
6
7Pet pet = new Dog("Fido", 3);
8Describe(pet);

1Fido the dog, age 3

Note the missing _ => arm. Before C# 15, a switch like this over an interface or abstract base class would give you a warning unless you added a discard at the end, because the compiler had no way of knowing nobody would add a Hamster somewhere. With a union it knows the full list (in other words it is exhaustive), so it can tell you when you’ve missed one.

Forgetting a case

Let’s add a pigeon (there’s always a pigeon, right?):

1public record Pigeon(string Name);
2
3public union Pet(Cat, Dog, Pigeon);

And leave Describe as it was:

1warning CS8509: The switch expression does not handle all possible values of its input type (it is not exhaustive). For example, the pattern 'Pigeon' is not covered.

A warning, that is. Soooo close, I mean, “impossible states made impossible” was literally right there! The program still builds and runs, and if a Pigeon ever reaches Describe it throws at runtime.

To be fair, F# does exactly the same thing:

1type Pet =
2    | Cat of name: string
3    | Dog of name: string * age: int
4    | Pigeon of name: string
5
6let describe pet =
7    match pet with
8    | Cat name -> $"{name} the cat"
9    | Dog (name, age) -> $"{name} the dog, age {age}"

1warning FS0025: Incomplete pattern matches on this expression. For example, the value 'Pigeon (_)' may indicate a case not covered by the pattern(s).

Elm is the only one of the three that refuses outright:

1-- MISSING PATTERNS ----------------------------------------------- src/Main.elm
2
3This `case` does not have branches for all possibilities:
4...
5Missing possibilities include:
6
7    Pigeon _
8
9I would have to crash if I saw one of those. Add branches for them!

“I would have to crash if I saw one of those.” Gotta love that one. And that’s kind of the whole point: The compiler knows the program can crash, and in C# and F# it says so politely and lets you ship it anyway. I’m getting sidetracked here, sorry.

So the first thing I’d do in any C# 15 codebase is turn that warning into an error. In a .csproj that’s <WarningsAsErrors>CS8509</WarningsAsErrors>; in a file-based app it’s one line at the top:

1#:property WarningsAsErrors=CS8509

1error CS8509: The switch expression does not handle all possible values of its input type (it is not exhaustive). For example, the pattern 'Pigeon' is not covered.
2
3The build failed. Fix the build errors and run again.

Much better. (I’d do the same for FS0025 in F#, for the record.)

Switch statements don’t count

Careful now: Exhaustiveness checking applies to switch expressions. The good old switch statement doesn’t get it:

 1Pet pet = new Pigeon("Kevin");
 2
 3switch (pet)
 4{
 5    case Cat c:
 6        Console.WriteLine($"feed {c.Name} some fish");
 7        break;
 8    case Dog d:
 9        Console.WriteLine($"walk {d.Name}");
10        break;
11}
12
13Console.WriteLine("done");

1done

I suppose one could argue that it’s consistent with how switch statements have always worked in C# (ie they’re allowed to do nothing), but it means the safety net only exists if you write your code a certain way. If I were adopting unions in an existing codebase, I’d want an analyzer that nudges every switch (someUnion) towards a switch expression. The closest built-in rule I found, IDE0010 (“Populate switch”), doesn’t help here: it fires on every switch statement, even one that covers all the union cases, because it wants a default: branch (which would defeat the purpose). Not too impressed here, to be perfectly honest.

Unions of types, not tags

This is the biggest conceptual difference from F# and Elm: In F#, the cases of a DU are tags: Email of string and Phone of string are two different cases even though both carry a string. A C# union is a union of types. The spec is upfront about this, and the compiler is too:

1public union ContactInfo(string, string);

1error CS0111: Type 'ContactInfo' already defines a member called 'ContactInfo' with the same parameter types

You can’t declare cases inline either, so every case has to be a type that exists somewhere. In practice that means a record per case, which is a little more ceremony than F#’s | Email of string. I’ll admit it pushes you towards something I’d recommend anyway: wrapping primitives in proper domain types (an EmailAddress record rather than a raw string). Scott Wlaschin would approve, I think.

The same thing hits generics in a sneakier and more subtle way way. Here’s your vanilla Result:

1public union Result<T, E>(T, E);
2
3Result<int, string> ok = 42;                          // fine
4Result<string, string> uhOh = "is this an error?";

1error CS0457: Ambiguous user defined conversions 'Result<string, string>.Result(string)' and 'Result<string, string>.Result(string)' when converting from 'string' to 'Result<string, string>'

The declaration compiles just fine. It’s only when T and E happen to be the same type that it falls apart, and the error shows up wherever you use it, not where you declared it. The fix is to wrap the cases (Ok<T> and Err<E> records), which brings us to the next point.

Bring your own Result

There’s no Result, Option, Bind or Map in the base library. Unions give you the general shape, and you write the rest. Here’s roughly the smallest version I could make work, using C# 14 extension blocks:

 1public record Ok<T>(T Value);
 2public record Err<E>(E Error);
 3public union Result<T, E>(Ok<T>, Err<E>);
 4
 5public static class ResultExtensions
 6{
 7    extension<T, E>(Result<T, E> r)
 8    {
 9        public Result<U, E> Bind<U>(Func<T, Result<U, E>> f) => r switch
10        {
11            Ok<T> ok => f(ok.Value),
12            Err<E> err => err,
13        };
14
15        public Result<U, E> Map<U>(Func<T, U> f) => r switch
16        {
17            Ok<T> ok => new Ok<U>(f(ok.Value)),
18            Err<E> err => err,
19        };
20    }
21}

With that in place, a small order flow (with its own error union) reads surprisingly close to the F# version:

 1public record InvalidEmail(string Input);
 2public record OutOfStock(string Sku);
 3public record PaymentDeclined(string Reason);
 4public union OrderError(InvalidEmail, OutOfStock, PaymentDeclined);
 5
 6static Result<Receipt, OrderError> PlaceOrder(string email, string sku, int qty) =>
 7    ParseEmail(email)
 8        .Map(e => new Order(e, sku, qty))
 9        .Bind(CheckStock)
10        .Bind(Charge);

And matching on the result, nested patterns included:

1static string Show(Result<Receipt, OrderError> r) => r switch
2{
3    Ok<Receipt> ok => $"OK: charged {ok.Value.Charged}",
4    Err<OrderError> { Error: InvalidEmail e } => $"bad email '{e.Input}'",
5    Err<OrderError> { Error: OutOfStock o } => $"out of stock: {o.Sku}",
6    Err<OrderError> { Error: PaymentDeclined p } => $"declined: {p.Reason}",
7};

1OK: charged 198
2bad email 'not-an-email'
3out of stock: DMMF-BOOK
4declined: card expired

Leave out one of the Err arms and you get CS8509 again, so the checking goes all the way down. That’s railway-oriented programming, for you, Scott Wlaschin style.In C#! With the compiler watching your back. I like it a lot.

My guess, though, is that every C# codebase will end up with its own slightly different Result<T, E> for a while. (Kotlin went through the same thing with Result vs Arrow’s Either, and rich errors are partly an attempt to end that.)

The value that isn’t any of them

Now watch this:

A union compiles to a struct. And every struct in C# has a default:

1Pet pet = default;
2Console.WriteLine(pet.Value is null);  // True
3
4var pets = new Pet[3];
5Console.WriteLine(pets[0].Value is null);  // True

So there’s a Pet that’s neither a Cat nor a Dog. And the Describe from earlier, which the compiler considers exhaustive (no warning at all), does this with it:

1Unhandled exception. System.Runtime.CompilerServices.SwitchExpressionException: Non-exhaustive switch expression failed to match its input.
2Unmatched value was Pet.

Same exception text as a forgotten Pigeon, by the way, so good luck telling the two apart in a log.

You don’t even need to write default yourself. An uninitialized field or a fresh array will hand you an empty Pet just the same. In Elm this state (obviously!!) simply doesn’t exist. F# isn’t completely immune (a DU is a class, so Unchecked.defaultof or Array.zeroCreate will give you a null one), but you have to go a bit out of your way, to say the least.

To its credit, the documentation says this out loud (“A default union contains null”), and recommends a null arm whenever default contents can reach your switch:

1static string Describe(Pet pet) => pet switch
2{
3    Cat c => $"{c.Name} the cat",
4    Dog d => $"{d.Name} the dog",
5    null => "no pet",
6};

Note that it says null, not _. A discard arm would also swallow that Pigeon, and then the compiler can’t warn you about it anymore. A null arm only catches the empty case.

It’s a reasonable trade-off given 25 years of C# and struct semantics. But it does mean C# unions make some impossible states impossible, and this particular one very possible.

Closed hierarchies

The other half of the feature is closed, which is closer to Kotlin’s sealed:

 1public closed record Shape;
 2public record Circle(double Radius) : Shape;
 3public record Square(double Side) : Shape;
 4public record Triangle(double Base, double Height) : Shape;
 5
 6static double Area(Shape shape) => shape switch
 7{
 8    Circle c => Math.PI * c.Radius * c.Radius,
 9    Square s => s.Side * s.Side,
10};

1warning CS8509: The switch expression does not handle all possible values of its input type (it is not exhaustive). For example, the pattern 'Triangle' is not covered.

A closed class can only be derived from inside its own assembly, and it’s implicitly abstract (new Shape() gives you CS0144). That makes it a nice fit for the “abstract base class plus a handful of records” pattern a lot of C# code already uses, and since it’s a class, there’s no struct default to worry about. (Plain old null, on the other hand, is still around.)

One detail from the docs: it isn’t transitive. A non-closed subclass of a closed class can be extended from other assemblies, so if you have a deeper hierarchy you’ll want closed on the intermediate levels too.

(Head spin: check!)

Boxing (yes, really)

The generated union stores whatever you put in it as a single object?. Reflecting over a union IntOrString(int, string):

1System.Object <Value>k__BackingField
2System.Runtime.CompilerServices.IUnion

So an int case gets boxed. For records (which are reference types anyway) this doesn’t matter, but if you were hoping for a zero-allocation int | string, the generated version sadly isn’t it. The docs describe a [Union] attribute pattern for hand-written unions with their own storage and a non-boxing TryGetValue access pattern. I’d expect library authors to use that, and the rest of us to never think about it.

And JSON?

Given my last post, I had to check:

1Pet pet = new Dog("Fido", 3);
2var json = JsonSerializer.Serialize(pet);
3// {"Name":"Fido","Age":3}
4
5JsonSerializer.Deserialize<Pet>(json);

1System.Text.Json.JsonException: JSON value type 'Object' is ambiguous for union type 'Pet' because multiple case types can use this value type. Specify a custom type classifier to support deserialization. Path: $ | LineNumber: 0 | BytePositionInLine: 1.

It serializes the case value with no tag, and then can’t read it back, because an object is an object. Which is the right call! Guessing would be worse. But it does mean that if you want unions on the wire, you’ll be making that decision explicitly, one way or another. (Also, if you’re trying this in a file-based app: reflection-based JSON is off by default there, so you need #:property JsonSerializerIsReflectionEnabledByDefault=true at the top, or you get an InvalidOperationException before you get anywhere near the union.)

Talking to F

Since unions are now in both languages, I tried consuming an F# DU from C#. It works, and C# 15 pattern matching on the generated case classes reads nicely. But C# doesn’t treat the F# DU as closed:

1warning CS8509: ... For example, the pattern '_' is not covered.

F# DUs don’t implement the new IUnion interface, so to C# they’re just a class hierarchy. Going the other way, F# sees a C# union as a struct with an object Value and has no idea it’s closed either. And closed is only enforced by the C# compiler: an F# project can happily inherit from a closed C# record in another assembly, which C# itself would reject. So if you have a mixed solution, I’d keep the domain types (and the matching on them) on one side of the boundary.

So is it any good?

Yes! More than I expected, actually. Coming from Elm, what I care about most is a closed set of cases and a compiler that tells me when I’ve missed one, and C# 15 has both (nested patterns included). Make CS8509 an error and add a null arm, and you get pretty close to making impossible states impossible.

It’s not F#. Cases are types rather than tags, there’s no Result in the box, and the struct default is a hole you have to remember to plug. And it’s very much not Elm, where none of those caveats exist and the compiler just says no. But C# was never going to be either of those, and given where it’s coming from, this is a big step in the right direction.

I still think F# is the nicer place to write a domain model. But if I do end up in a C# codebase, I know which warning I’m turning into an error first :D
