Interface Segregation: Why Your Interfaces Should Be Small and Focused

2025-01-14 #architecture #solid #clean-architecture #go #golang #interfaces

Introduction

In our previous post, we explored the Dependency Inversion Principle and how it enables clean, modular architectures. Today, let’s dive into another crucial SOLID principle: Interface Segregation.

Again, kudos to Uncle Bob for reminding me about the importance of good software architecture in his classic Clean Architecture! That book is my primary inspiration for this series. Without clean architecture, we’ll all be building firmware (my paraphrased summary).

The Interface Segregation Principle (ISP) states that clients should not be forced to depend on interfaces they don’t use.

This principle might sound obvious, but its violation is surprisingly common. Let’s explore why it matters and how to apply it effectively.

The Problem with “Fat” Interfaces

Consider this common anti-pattern in many codebases:

 1// DON'T DO THIS
 2type UserService interface {
 3    CreateUser(user User) error
 4    GetUser(id string) (User, error)
 5    UpdateUser(user User) error
 6    DeleteUser(id string) error
 7    ValidatePassword(password string) bool
 8    SendWelcomeEmail(user User) error
 9    GenerateAuthToken(user User) (string, error)
10    ResetPassword(email string) error
11    UpdateLastLogin(id string) error
12}

This interface violates ISP because:

  1. Most clients only need a subset of these methods
  2. Changes to any method affect all implementations
  3. Testing becomes unnecessarily complex

Better: Small, Focused Interfaces

Instead, we should break this down into role-specific interfaces that each serve a single responsibility:

 1type UserReader interface {
 2    GetUser(id string) (User, error)
 3}
 4
 5type UserWriter interface {
 6    CreateUser(user User) error
 7    UpdateUser(user User) error
 8    DeleteUser(id string) error
 9}
10
11type UserAuthenticator interface {
12    ValidatePassword(password string) bool
13    GenerateAuthToken(user User) (string, error)
14    UpdateLastLogin(id string) error
15}
16
17type UserNotifier interface {
18    SendWelcomeEmail(user User) error
19}

Now clients can depend only on what they need:

1type UserProfileHandler struct {
2    reader UserReader
3}
4
5type UserRegistrationHandler struct {
6    writer  UserWriter
7    auth    UserAuthenticator
8    notifier UserNotifier
9}

The Power of Composition

Go’s interface composition makes this pattern particularly elegant:

1// When you do need everything
2type CompleteUserService interface {
3    UserReader
4    UserWriter
5    UserAuthenticator
6    UserNotifier
7}

This approach gives us several benefits:

  1. Flexibility: Implementations can be mixed and matched
  2. Testability: Mocking becomes trivial
  3. Maintainability: Changes affect fewer components
  4. Clarity: Interfaces document their purpose through focus

Real-World Example: HTTP Handlers

Let’s see how this applies to a typical web service:

 1type UserHandler struct {
 2    reader UserReader
 3    writer UserWriter
 4}
 5
 6func (h *UserHandler) GetUser(w http.ResponseWriter, r *http.Request) {
 7    // Only needs UserReader
 8    id := chi.URLParam(r, "id")
 9    user, err := h.reader.GetUser(id)
10    // ... handle response
11}
12
13func (h *UserHandler) CreateUser(w http.ResponseWriter, r *http.Request) {
14    // Only needs UserWriter
15    var user User
16    if err := json.NewDecoder(r.Body).Decode(&user); err != nil {
17        http.Error(w, err.Error(), http.StatusBadRequest)
18        return
19    }
20
21    if err := h.writer.CreateUser(user); err != nil {
22        http.Error(w, err.Error(), http.StatusInternalServerError)
23        return
24    }
25
26    w.WriteHeader(http.StatusCreated)
27}

Testing Benefits

Small interfaces make testing much simpler:

 1type mockUserReader struct {
 2    users map[string]User
 3}
 4
 5func (m *mockUserReader) GetUser(id string) (User, error) {
 6    if user, ok := m.users[id]; ok {
 7        return user, nil
 8    }
 9    return User{}, errors.New("user not found")
10}
11
12func TestGetUser(t *testing.T) {
13    mock := &mockUserReader{
14        users: map[string]User{
15            "123": {ID: "123", Name: "Test User"},
16        },
17    }
18
19    handler := &UserHandler{reader: mock}
20    // Test your handler with a simple mock
21}

Key Takeaways

  1. Keep interfaces small and focused - they should do one thing well
  2. Let clients define interfaces - don’t force unnecessary dependencies
  3. Use composition when you need to combine functionality
  4. Think in terms of roles rather than objects

Conclusion

Interface Segregation might seem like extra work initially, but it pays dividends in maintainability, testability, and flexibility. Combined with Dependency Inversion from our previous post, these principles form a powerful foundation for clean, maintainable architectures.

Stay tuned for our next post in the series, where we’ll explore the Liskov Substitution Principle!

Pro tip: When in doubt about interface size, err on the side of making them too small. It’s easier to compose small interfaces than to break apart large ones.
