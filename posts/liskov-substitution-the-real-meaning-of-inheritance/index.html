Liskov Substitution: The Real Meaning of Inheritance

2025-01-21 #architecture #solid #clean architecture #kotlin #inheritance

Introduction

After exploring Dependency Inversion and Interface Segregation, let’s tackle perhaps the most misunderstood principle of SOLID: The Liskov Substitution Principle (LSP).

Again, kudos to Uncle Bob for reminding me about the importance of good software architecture in his classic Clean Architecture! That book is my primary inspiration for this series. Without clean architecture, we’ll all be building firmware (my paraphrased summary).

The Liskov Substitution Principle states that if S is a subtype of T, then objects of type T may be replaced with objects of type S without altering any of the desirable properties of the program.

In simpler terms: subtypes must be substitutable for their base types. Let’s see what this really means in practice.

The Classic Rectangle-Square Problem

This is the canonical example of LSP violation:

 1open class Rectangle {
 2    open var width: Int = 0
 3    open var height: Int = 0
 4
 5    fun area() = width * height
 6}
 7
 8// This seems logical, but violates LSP
 9class Square : Rectangle() {
10    override var width: Int = 0
11        set(value) {
12            field = value
13            height = value
14        }
15
16    override var height: Int = 0
17        set(value) {
18            field = value
19            width = value
20        }
21}
22
23// This code will fail for Square
24fun resizeRectangle(rectangle: Rectangle) {
25    rectangle.width = 4
26    rectangle.height = 5
27    assert(rectangle.area() == 20) // Fails for Square!
28}

The problem? While mathematically a square is a rectangle, in terms of behavior substitutability, it isn’t. The Square class violates LSP because it changes the behavior that clients of Rectangle expect.

A Better Approach

Instead of inheritance, we can use composition and interfaces:

 1interface Shape {
 2    fun area(): Int
 3}
 4
 5class Rectangle(
 6    var width: Int,
 7    var height: Int
 8) : Shape {
 9    override fun area() = width * height
10}
11
12class Square(
13    var side: Int
14) : Shape {
15    override fun area() = side * side
16}

Real-World Example: Payment Processing

Let’s look at a more practical example involving payment processing:

 1interface PaymentProcessor {
 2    fun processPayment(amount: Money): Result<Transaction>
 3}
 4
 5class CreditCardProcessor : PaymentProcessor {
 6    override fun processPayment(amount: Money): Result<Transaction> {
 7        // Process credit card payment
 8        return Result.success(Transaction(amount))
 9    }
10}
11
12class DebitCardProcessor : PaymentProcessor {
13    override fun processPayment(amount: Money): Result<Transaction> {
14        // Process debit card payment
15        return Result.success(Transaction(amount))
16    }
17}
18
19// This works with any PaymentProcessor
20class CheckoutService(
21    private val paymentProcessor: PaymentProcessor
22) {
23    fun checkout(cart: ShoppingCart) {
24        val amount = cart.total()
25        paymentProcessor.processPayment(amount)
26            .onSuccess { transaction ->
27                // Handle success
28            }
29            .onFailure { error ->
30                // Handle failure
31            }
32    }
33}

Common LSP Violations

1. Throwing Unexpected Exceptions

 1interface UserRepository {
 2    fun findById(id: String): User?
 3}
 4
 5// LSP Violation: Throws instead of returning null
 6class CachedUserRepository : UserRepository {
 7    override fun findById(id: String): User? {
 8        throw NotImplementedError("Cache not initialized")
 9        // Should return null if not found
10    }
11}

2. Returning Null When Base Type Doesn’t

 1interface DataFetcher {
 2    fun fetchData(): List<String>
 3}
 4
 5// LSP Violation: Returns null when base contract promises List
 6class RemoteDataFetcher : DataFetcher {
 7    override fun fetchData(): List<String> {
 8        return if (isConnected()) {
 9            listOf("data")
10        } else {
11            null // Violation! Should return empty list
12        }
13    }
14}

How to Ensure LSP Compliance

  1. Use Contract Tests
 1abstract class PaymentProcessorTest {
 2    abstract fun createProcessor(): PaymentProcessor
 3
 4    @Test
 5    fun `should process valid payment`() {
 6        val processor = createProcessor()
 7        val result = processor.processPayment(Money(100))
 8        assert(result.isSuccess)
 9    }
10
11    @Test
12    fun `should handle zero amount`() {
13        val processor = createProcessor()
14        val result = processor.processPayment(Money(0))
15        assert(result.isSuccess)
16    }
17}
18
19class CreditCardProcessorTest : PaymentProcessorTest() {
20    override fun createProcessor() = CreditCardProcessor()
21}
22
23class DebitCardProcessorTest : PaymentProcessorTest() {
24    override fun createProcessor() = DebitCardProcessor()
25}
  1. Document Preconditions and Postconditions
 1interface AccountService {
 2    /**
 3     * Withdraws money from account
 4     *
 5     * Preconditions:
 6     * - Amount must be positive
 7     * - Account must exist
 8     * - Account must have sufficient balance
 9     *
10     * Postconditions:
11     * - Account balance is reduced by amount
12     * - Returns success with transaction details
13     * - Never throws exceptions (uses Result)
14     */
15    fun withdraw(accountId: String, amount: Money): Result<Transaction>
16}

Key Takeaways

  1. Inheritance isn’t always the answer - prefer composition when behavior differs
  2. Think in terms of contracts - subtypes must fulfill the base type’s contract
  3. Use contract tests to verify LSP compliance
  4. Document pre/postconditions clearly
  5. Return types matter - be consistent with null/non-null, exceptions, etc.

Conclusion

Liskov Substitution Principle is about more than just inheritance - it’s about behavioral compatibility and meeting expectations. When followed properly, it leads to more reliable and maintainable code by ensuring that components are truly interchangeable.

Pro tip: If you find yourself writing comments like “don’t use X in Y way” or “this override behaves differently”, you might be violating LSP.
