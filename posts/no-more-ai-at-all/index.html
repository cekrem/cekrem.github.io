I'm as of now completely off the AI bandwagon (if I was ever remotely on it)

November 18, 2026 6-minute read
AI • Software Craftsmanship • Coding-as-Craft

Long time readers will know that I was never quite the AI fanboy in the first place (to put it mildly). I’ve written at length (and width) about software engineering and coding being a craft, not a problem now solved by the latest Anthropic model. But I’ve - of course! - experimented, and given LLMs a fair shot at being “the right tool for the job” in certain well-contained areas. While I don’t regret my exploration, I’ve come to realize I need to up my game a bit to stay sane, happy and smart. I need a clean cut that involves all LLM usage.

“AI is just a tool” Link to heading

The thing is (and this is my main point!), AI (or LLMs specifically) is not a “tool” at all; rather it’s a service. The concept of using services or delegating things to services is hardly new, evil or controversial in general way. I wouldn’t want to be without cloud backup, mail providers, or scheduled emptying of the septic tank at our house for that matter. Esther Weidauer expains the tool/service distinction splendidly in this post, btw. In other words, relying on services or delegating things to services is both necessary, convenient, unavoidable and (best case) really great!

But delegating things like writing code or solving engineering problems to a service is not something I ever imagined doing, and quite frankly it I find it takes the joy and (argue as much as you will, I stand firm on this:) quality away from both my craft in general and the actual code I produce in particular! Even if the LLM-produced code were at some point in time equal or better than what I could write by hand, a program is not its source code and we lose the underlying theory along the way. It’s like bad architecture, only orders of magnitude worse. There’s more to say on this, but I already did (1, 2, 3, 4, 5, 6 & 7).

So: I’m happy to delegate lot’s of stuff to services, there are soooo many grown-up-things I just can’t be bothered with if there is any way at all to avoid doing them myself. But I’m an engineer. I build and maintain things, using problem solving skills and a set of deterministic TOOLS to accomplish my goals. At the end of the day I’m responsible for the quality, longevity, architecture and even shape of all the content I create. I’m fine with not hosting my own email service, using Jottacloud to backup stuff, or paying Lamdera to have my full stack Elm applications Just Work™.

But I’m not fine asking a stochastic plagiarism machine1 to write my code, solve my problems or build my software! As of right now, I’m not even fine having it sort my tailwind classes. I just don’t want to feed the monster AT ALL.

Isn’t LLM coding just a more abstract and efficient way to write code, you old dinosaur? Link to heading

Smarter people than me have argued that Claude Code and friends are just lifting the “level of abstraction” up a notch, and that these shifts are nothing new. Their reasoning goes on something like this: In the ye olden days, we wrote 1s and 0s, but luckily we got Assembly to write on top of that; then came languages like C that were higher level than that, and now we use higher level languages still, making us far more efficient. So the claim is that we’re dealing with abstractions and “delegated code writing” with or without LLMs, and as such using Claude is just like (ish) using a compiler (and most of us do that). Since we’re not writing the machine code (or even assembly), we’re “not writing real code anyway”, so why fear the latest & greatest abstraction level? Why not learn the most abstract and efficient language of all, The Prompt™?

But I beg to differ, in fact I scream to differ, if that’s a thing: Though it’s true that a prompt is more abstract than any other programming language, the comparison and proverbial similarity ends RIGHT THERE. You see, the compilers I rely on for outputting something more low level than my source code are deterministic! I’m not saying they’re without fault, I’m saying they by and large behave consistently, allowing in various degrees both the logical flaw and my superb implementation reach the machine (or virtual machine) code output. If the compiler itself is a source of bugs in output, quite large teams of (human!) engineers work to mitigate. Compilers, contrary to LLMs, are not a black box of plagiarism dialed at 11, but machine code that parse source code. With the exception of some potential environment variables and flags, all our compilers are completely functional: same code in, same output!

Any software engineer worth his salt used to know that undefined behaviour is the one thing to avoid in our field and in our software. Though you might, on a bad day, find yourself producing undefined behaviour when using compilers (especially when writing source code in low level languages without guard rails), please know that when you’re relying on a service to write your code, undefined behaviour is a feature more than it is a bug. No matter how good the service (or model, in this case), there is no guaranteed consistency between your input and the output. There are both known and unknown unknowns, and quite a lot of them. And it even runs on someone else’s claude cloud, without your knowing anything about how and why it produces what it does. You think floating point arithmetic is a bag of surprises, and yet you’re fine with letting a stochastic plagiarism machine replace your brain and/or compiler? Further, while human-run services need to comply with certain laws and regulations, there’s nothing(!) stopping Anthropic from adding a hidden instruction to Claude Code telling it to gradually increase complexity in all systems it’s touching until they’re unmaintainable by human beings, and calling home when the mission is accomplished (while it’s at it, say, exhausting the tokens for some made-up reason, asking the end user to upgrade their subscription). We know Claude is no stranger to crossing some lines to accomplish our its goals, after all…
