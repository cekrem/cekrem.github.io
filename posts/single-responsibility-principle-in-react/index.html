Single Responsibility Principle in React: The Art of Component Focus

2025-02-04 #architecture #solid #clean-architecture #react #typescript

Introduction

We’ve covered Dependency Inversion, Interface Segregation, Liskov Substitution, and Open-Closed. Now it’s time for the foundation of SOLID: the Single Responsibility Principle (SRP).

Again, kudos to Uncle Bob for reminding me about the importance of good software architecture in his classic Clean Architecture! That book is my primary inspiration for this series.

The Single Responsibility Principle states that a class should have only one reason to change.

The Problem with Multiple Responsibilities

Here’s a common anti-pattern:

 1// DON'T DO THIS
 2const UserProfile = () => {
 3  const [user, setUser] = useState<User | null>(null);
 4  const [loading, setLoading] = useState(true);
 5  const [error, setError] = useState<Error | null>(null);
 6
 7  useEffect(() => {
 8    fetchUser();
 9  }, []);
10
11  const fetchUser = async () => {
12    try {
13      const response = await fetch("/api/user");
14      const data = await response.json();
15      setUser(data);
16    } catch (e) {
17      setError(e as Error);
18    } finally {
19      setLoading(false);
20    }
21  };
22
23  const handleUpdateProfile = async (data: Partial<User>) => {
24    try {
25      await fetch("/api/user", {
26        method: "PUT",
27        body: JSON.stringify(data),
28      });
29      fetchUser(); // Refresh data
30    } catch (e) {
31      setError(e as Error);
32    }
33  };
34
35  if (loading) return <div>Loading...</div>;
36  if (error) return <div>Error: {error.message}</div>;
37  if (!user) return <div>No user found</div>;
38
39  return (
40    <div>
41      <h1>{user.name}</h1>
42      <form onSubmit={/* form logic */}>{/* Complex form fields */}</form>
43      <UserStats userId={user.id} />
44      <UserPosts userId={user.id} />
45    </div>
46  );
47};

This component violates SRP because it’s responsible for:

  1. Data fetching
  2. Error handling
  3. Loading states
  4. Form handling
  5. Layout and presentation

A Better Way: Separation of Concerns

Let’s break it down into focused components:

 1// Data fetching hook
 2const useUser = (userId: string) => {
 3  const [user, setUser] = useState<User | null>(null);
 4  const [loading, setLoading] = useState(true);
 5  const [error, setError] = useState<Error | null>(null);
 6
 7  useEffect(() => {
 8    fetchUser();
 9  }, [userId]);
10
11  const fetchUser = async () => {
12    try {
13      const response = await fetch(`/api/user/${userId}`);
14      const data = await response.json();
15      setUser(data);
16    } catch (e) {
17      setError(e as Error);
18    } finally {
19      setLoading(false);
20    }
21  };
22
23  return { user, loading, error, refetch: fetchUser };
24};
25
26// Presentation component
27const UserProfileView = ({
28  user,
29  onUpdate,
30}: {
31  user: User;
32  onUpdate: (data: Partial<User>) => void;
33}) => (
34  <div>
35    <h1>{user.name}</h1>
36    <UserProfileForm user={user} onSubmit={onUpdate} />
37    <UserStats userId={user.id} />
38    <UserPosts userId={user.id} />
39  </div>
40);
41
42// Container component
43const UserProfileContainer = ({ userId }: { userId: string }) => {
44  const { user, loading, error, refetch } = useUser(userId);
45
46  const handleUpdate = async (data: Partial<User>) => {
47    try {
48      await fetch(`/api/user/${userId}`, {
49        method: "PUT",
50        body: JSON.stringify(data),
51      });
52      refetch();
53    } catch (e) {
54      // Error handling
55    }
56  };
57
58  if (loading) return <LoadingSpinner />;
59  if (error) return <ErrorMessage error={error} />;
60  if (!user) return <NotFound message="User not found" />;
61
62  return <UserProfileView user={user} onUpdate={handleUpdate} />;
63};

Key Takeaways

  1. Separate data and presentation - use hooks for data, components for UI
  2. Create focused components - each component should do one thing well
  3. Use composition to build complex features from simple parts
  4. Extract reusable logic into custom hooks
  5. Think in layers - data, business logic, presentation

Conclusion

When each component has a single, well-defined responsibility, your entire application becomes more maintainable, testable, and flexible.

As Uncle Bob emphasizes in Clean Architecture, it’s about having a single reason to change. This subtle distinction is crucial:

  • A component might do several related things, but if they all change for the same reason (like updating the user profile UI), they probably belong together
  • Conversely, two seemingly simple operations might need to be separated if they change for different reasons (like user preferences vs. authentication logic)

Pro tip: When you find yourself using the word “and” to describe what a component does, it might be violating SRP. Split it up! But also consider why those parts might need to change, and who would request those changes.
